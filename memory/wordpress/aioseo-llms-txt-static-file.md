---
name: AIOSEO writes llms.txt as a static file at the web root
description: AIOSEO Pro generates llms.txt to disk rather than through PHP, so it freezes at deploy — production serves whatever machine last generated it, with a 366-day asset TTL and no way to purge it
type: reference
---

All in One SEO **Pro 4.8.4+** ships an `llms.txt` feature that writes a **physical file to the web root**, not a route rendered through PHP:

```php
// app/Common/Llms/Llms.php
public function getFilePath( $full = false ) {
  return trailingslashit( dirname( WP_CONTENT_DIR ) ) . ( $full ? 'llms-full.txt' : 'llms.txt' );
}
```

It is regenerated by a recurring action-scheduler job (`aioseo_generate_llms_txt`, `DAY_IN_SECONDS`). That one design choice causes three separate problems, and they compound:

**1. It bakes in whatever domain generated it.** Run the site under ddev and the daily job fires locally, rewriting every URL at `home_url()` — i.e. `https://<project>.ddev.site`. The file is tracked in git, so it surfaces as an ordinary modification and rides along in the next commit. AIOSEO's entry ordering isn't stable either, so each regeneration reshuffles hundreds of lines for zero semantic change — the diff looks like real work and reviews right past.

**2. On Pantheon it can never self-heal.** The code directory is read-only on test/live, so the daily job cannot overwrite the deployed copy. The committed bytes are what gets served, indefinitely. Confirmed on atrix.com: production `/llms.txt` was **byte-identical** (`md5`, 104854 bytes) to `git show HEAD:llms.txt`, all 583 URLs pointing at `atr.ddev.site`, content traceable to a commit three weeks earlier.

**3. nginx serves it as a static asset.** Because it is a real file on disk, it inherits Pantheon's static-asset headers — `Cache-Control: max-age=31622400` (366 days) and a weak `mtime-size` etag, exactly what a minified JS file gets. Nothing in the repo sets that; it is the platform default for anything served off disk. A **Cloudflare purge does not help**: `.txt` isn't in Cloudflare's default cacheable set, so it returns `cf-cache-status: DYNAMIC` and the Pantheon edge (`age:`) is what actually holds it. Browser and crawler copies can't be recalled at all, and `llms.txt` is a fixed path so there's no cache-busting filename.

**The one-command diagnosis** is to compare against a sibling the same plugin renders dynamically:

```
/sitemap.xml → https://atrix.com      (through PHP — home_url() at request time, correct)
/llms.txt    → https://atr.ddev.site  (static file from the repo — frozen at deploy)
```

Same plugin, same data. Dynamic is right; the file on disk is stale.

**Impact is genuinely low — don't inflate it.** Nothing human-facing renders `llms.txt`, no major search engine uses it (Google has said so explicitly), and AI crawlers are carried by `sitemap.xml` and the HTML regardless. The real cost is repo hygiene: a ~100KB generated artifact churning hundreds of lines into commits, which is also how the bad content shipped. Treat it as cleanup, not an incident.

**Fixes**, cheapest first:

- `.gitignore` it and `git rm --cached llms.txt`. Live ends up with no `llms.txt` at all, which given the above costs nothing measurable.
- Serve it dynamically from a small mu-plugin (disable AIOSEO's static generation). Renders at `home_url()` every time, gets normal WordPress cache headers instead of the asset TTL, and leaves the repo entirely.
- Rewriting the domain before commit (`sed`, or a pre-push hook) works but only treats the symptom — the file still ships frozen and still carries the year-long TTL.

**How to apply:** Generalize past AIOSEO — **any plugin that writes a generated file into the web root behaves this way on Pantheon**: correct locally, frozen at deploy, and served with a year-long asset TTL. When something on production shows the wrong environment's domain, check whether it is a file on disk before hunting through code or the database; if it is, prefer moving it to a dynamic route over patching the contents.
