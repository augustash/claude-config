---
name: WP security-header CSP silently breaks analytics
description: An enforced CSP on a WP site silently blackholes GA4/GTM/Google-Ads beacons — analytics cliffs overnight while the site looks fine. Two header plugins enforce the INTERSECTION. Diagnose via violation log + connect-src diff (not the repo); fix by right-sizing to a Tier-1 scheme-permissive policy in code.
type: reference
---

**Symptom:** GA4 "Active users" falls off a cliff overnight (e.g. ~150/day → ~10/day, then dead flat) with no gradual ramp, right after a "security hardening" pass. Site works fine, real conversions (form fills) hold steady. A vertical cliff to a flat floor = **measurement broke**, not visitors left (real traffic loss ramps down over days as Google recrawls). Blast radius is usually wider than GA: the same incomplete `connect-src` also kills **Google Ads conversion + remarketing** (`www.google.com` ccm/collect, `www.googleadservices.com`, `googleads.g.doubleclick.net`, `stats.g.doubleclick.net`) — tell the client to annotate the gap in Ads too, not just GA.

**Cause:** an **enforced** CSP whose allowlist is narrower than what the site loads. The tell that fools everyone: the allowlist usually includes `googletagmanager.com` + `www.google-analytics.com` (so the *script* loads and the page looks fine) but omits the actual beacon host — commonly `analytics.google.com` (GA4 often routes `/g/collect` there, NOT to `google-analytics.com`). `script-src` lets the tag *load*; `connect-src` governs the *beacon* — a stricter connect-src silently drops hits with no console "blocked" error.

**Two-plugin intersection (the trap):** more than one plugin can emit CSP, and browsers enforce the **intersection** of all CSP headers (a resource must pass *every* policy) — not last-wins. So the header you read may be innocent while a second one does the blocking, and toggling one plugin does nothing. Fingerprints: **RSSSL Pro** = granular allowlist + a `report-uri` (`/wp-json/.../csp`), mode in `rsssl_options['csp_status']` (`disabled`|`learning_mode`|enforce). **Headers Security Advanced & HSTS** = free-text CSP in the `hsts_csp` option written to `.htaccess`, emits `Content-Security-Policy` from `hsts_plugin_get_csp_header()` **and** a legacy `X-Content-Security-Policy` (that legacy `X-` header is its signature; modern browsers ignore it). **Never run two security-header plugins** — consolidate to one. Blanking Headers Security's textarea reverts to its default `upgrade-insecure-requests;` (harmless); fully removing needs deactivation (and check `.htaccess` for leftover `Header set …` lines).

**Diagnose:**
- Live header, real browser UA (some setups skip `curl -I`/HEAD): `curl -sD - -A 'Mozilla/5.0' https://SITE/ -o /dev/null | grep -i security-policy`. Enforcing = `content-security-policy:`; report-only = `-report-only:`.
- The receipt: `wp_rsssl_csp_log` (cols `time, documenturi, violateddirective, blockeduri, status`) lists every source RSSSL saw in learning. Diff it against the enforced `connect-src`; logged-but-absent = blocked.
- Prove beacon-vs-script: headless Chrome `--log-net-log=out.json --virtual-time-budget=12000 --dump-dom URL`, then grep `/g/collect` (GA4 hit) vs `ccm/collect` (Google-tag ping). Netlog logs even blocked requests, so **absence of `/g/collect` = GA never attempted it** (consent/config), while a blocked-but-present request = CSP. Post-fix this flips from 0 to many `analytics.google.com/g/collect?tid=G-…`.

**Right-size before you enforce — Tier 1 vs Tier 2:** a strict host-allowlist (Tier 2) is overkill for a marketing/brochure site with no payments/auth/PII, *especially* because WordPress + GTM force `'unsafe-inline'`/`'unsafe-eval'` in `script-src` — which guts most of CSP's value and which even the strictest scanners flag on BOTH tiers, so Tier 2 buys ~no better grade for real maintenance cost + break risk. Customers' security requirements attach to the systems that hold their data (portals, processing), not the brochure site; third-party rating scanners (SecurityScorecard/BitSight) are satisfied by Tier 1's mere presence of a sane CSP. **Tier 1** = `default-src 'self'` (clears the `default-src` `*`/`unsafe-inline`/`data:` findings) + expensive directives permissive by *scheme* (`https:`) so there's no host list to maintain and a new tag can never be blackholed, while keeping the cheap wins strict (`frame-ancestors 'self'`, `object-src 'none'`, `base-uri 'self'`). Reference implementation: `vendor/augustash/claude-config/templates/wordpress/csp-tier1.php` (front-end-only plugin; put CSP in reviewed code, not a fat-fingerable admin textarea — that textarea *is* the root cause). Escalate to Tier 2 only on a real requirement: deactivate the Tier-1 plugin, set RSSSL `csp_status='learning_mode'` ~1 week, verify `connect-src` carries every Google host, then enforce with `report-uri` monitoring left on.

**Google measurement hosts a Tier-2 `connect-src` must carry** (also some in `img-src`): `googletagmanager.com`, `www.google-analytics.com`, `region1.google-analytics.com`, `analytics.google.com`, `region1.analytics.google.com`, `www.google.com`, `stats.g.doubleclick.net`, `googleads.g.doubleclick.net`, `ad.doubleclick.net`, `www.googleadservices.com`. Note `region1.google-analytics.com` ≠ `region1.analytics.google.com` — distinct hosts.

**How to apply:** analytics "died" after a security change on an augustash WP site → check enforced CSP headers first, it's not in git. RSSSL runtime artifacts are server-managed — gitignore `wp-content/rsssl-managed-htaccess.lock` (sits with `advanced-headers.php`). See [[woocommerce-pantheon-cache]] for the general "traffic anomaly is a plugin/DB setting, not code" posture.
